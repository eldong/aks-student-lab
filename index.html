Beginner-friendly combined lab · Windows PowerShell · Existing AKS cluster required

Learn namespace governance, VPA, and HPA with one guided student workbook

This lab combines three existing advanced-topic demos into one student-focused experience. You will see how Kubernetes enforces per-container defaults and namespace budgets, how Vertical Pod Autoscaler recommends better requests, and how Horizontal Pod Autoscaler scales replicas up and down under CPU load.

Module 1 · LimitRange and ResourceQuota Module 2 · Vertical Pod Autoscaler Module 3 · Horizontal Pod Autoscaler Copy-ready commands One PowerShell window

What to expect

  • Run all commands from the student-lab folder.
  • Use the manifests included in this cloned repository under .\manifests.
  • Use kubectl for all three modules and az only for the VPA add-on check or enable step.
  • See realistic delays: metrics are not instant, and VPA recommendations take time.
  • Clean up only the demo namespaces when you finish.

Preflight

Open the correct folder and define the lab variables

Start in the right working directory so all of the relative manifest paths work.

Objective

Prepare one PowerShell session you can reuse across all three modules.

Why this matters

The commands in this workbook rely on relative paths inside this cloned repository. If you run from the wrong folder, the manifests will not be found. The variables below also persist only in the current PowerShell window.

Run this once at the start of the lab
Get-Location
if ([string]::IsNullOrWhiteSpace($RESOURCE_GROUP)) { throw 'RESOURCE_GROUP is not set.' }
if ([string]::IsNullOrWhiteSpace($AKS_NAME)) { throw 'AKS_NAME is not set.' }
if ([string]::IsNullOrWhiteSpace($ACR_NAME)) { throw 'ACR_NAME is not set.' }
code .
$rg = $RESOURCE_GROUP
$aksName = $AKS_NAME
$acrName = $ACR_NAME
$location = az aks show --resource-group $rg --name $aksName --query location -o tsv
$limitNs = 'aks-governance-demo'
$vpaNs = 'aks-vpa-demo'
$hpaNs = 'aks-hpa-demo'
"AKS: $aksName | Resource group: $rg | ACR: $acrName | Region: $location"

Command explanation

  • Open PowerShell in the cloned repository folder before running these commands.
  • Get-Location confirms the folder from which relative manifest paths will be resolved.
  • The first three checks stop immediately with a clear message if an instructor-provided variable is missing.
  • code . opens the current lab folder in Visual Studio Code so you can inspect the manifests while working through the exercises.
  • $rg, $aksName, and $acrName are short aliases for the supplied variables.
  • $location reads the cluster's Azure region instead of assuming one.
  • $limitNs, $vpaNs, and $hpaNs keep the namespace names easy to reuse.
  • Get-Location gives you quick proof that the folder is correct.
Expected output / evidence

Get-Location shows the cloned repository folder, Visual Studio Code opens that folder, and the final line prints the supplied AKS cluster, resource group, ACR, and detected Azure region.

Troubleshooting note

If the folder is wrong, run Set-Location <path-to-your-cloned-repository>. If a variable is missing, stop and ask the instructor for the setup command. Opening a new PowerShell window can clear ordinary PowerShell variables, so rerun the instructor setup first.

Module 1 · LimitRange and ResourceQuota

Create the governance namespace and apply a LimitRange

Start with per-container defaults and boundaries before you introduce a namespace-wide quota.

Objective

Create the demo namespace and apply a LimitRange that sets default requests, default limits, and maximum allowed values.

Why this matters

A LimitRange helps platform teams establish safe defaults. It can fill in missing resource requests and limits, and it can reject individual containers that ask for too much.

Review before deploying

In VS Code, open 00-namespace.yaml and review the namespace definition before applying it.

Create the namespace and inspect the label
kubectl apply -f .\manifests\01-limit-ranges-resource-quotas\00-namespace.yaml
kubectl get namespace $limitNs --show-labels
Review before deploying

In VS Code, open 10-limit-range.yaml and identify the default requests, default limits, and maximum values before applying it.

Apply the LimitRange and inspect its policy
kubectl apply -f .\manifests\01-limit-ranges-resource-quotas\10-limit-range.yaml
kubectl describe limitrange container-resource-limits -n $limitNs
LimitRange

A namespace policy that sets default, minimum, or maximum resources for containers or pods.

Default request

The amount of CPU or memory Kubernetes will inject when a developer does not specify a request.

Default limit

The runtime cap Kubernetes will inject when a developer omits a limit.

Maximum

The largest per-container value this namespace will admit.

Command explanation

  • The namespace manifest creates aks-governance-demo with a demo label.
  • kubectl describe limitrange is the easiest way to read the effective defaults and max values.
  • In this demo, the important numbers are default request 100m / 64Mi, default limit 300m / 128Mi, and maximum 500m / 256Mi.
Expected output / evidence

The namespace exists with the demo label. The LimitRange description shows default requests of 100m CPU and 64Mi memory, default limits of 300m CPU and 128Mi memory, and a maximum of 500m CPU and 256Mi memory.

Troubleshooting note

If the namespace already exists from an earlier run, that is okay. If you want a fully clean rerun, delete $limitNs before reapplying and wait until it is gone.

Checkpoint / question

Does a LimitRange control one container's settings, the entire namespace budget, or both?

Module 1

See the LimitRange inject defaults and reject an oversized pod

Use one pod with no resources and one pod above the maximum to show both sides of the policy.

Objective

Prove that Kubernetes can both supply missing resource settings and deny requests that exceed the policy.

Why this matters

This is a common governance pattern. Developers can omit small resource details safely, but they cannot accidentally request values above the namespace maximum.

Review before deploying

In VS Code, open 20-defaulted-pod.yaml and confirm that the container does not define resource requests or limits.

Create a pod with no explicit resources and inspect the injected values
kubectl apply -f .\manifests\01-limit-ranges-resource-quotas\20-defaulted-pod.yaml
kubectl wait --for=condition=Ready pod/defaulted-pod -n $limitNs --timeout=90s
kubectl get pod defaulted-pod -n $limitNs -o jsonpath="{.spec.containers[0].resources}"
Review before deploying

In VS Code, open 30-over-limit-pod.yaml and find the resource value that exceeds the LimitRange maximum.

Try to create a pod above the LimitRange maximum
kubectl apply -f .\manifests\01-limit-ranges-resource-quotas\30-over-limit-pod.yaml

Defaulted pod

Because the manifest omitted resources, Kubernetes injects the LimitRange defaults during admission.

Over-limit pod

Because the manifest requests 600m CPU and 300Mi memory, the API server rejects it before it is created.

Command explanation

  • kubectl wait pauses until the defaulted pod is actually Ready.
  • The JSONPath command reads the resources that ended up on the live pod spec.
  • The over-limit manifest is intentionally invalid for this namespace so you can see the admission error.
Expected output / evidence

The defaulted pod should become Ready and show requests of 100m / 64Mi and limits of 300m / 128Mi. The oversized pod should be rejected with a forbidden error because it exceeds the LimitRange maximum.

Troubleshooting note
  • If kubectl wait times out, run kubectl get pods -n $limitNs and kubectl describe pod defaulted-pod -n $limitNs to check for image pull problems.
  • If the oversized pod is created successfully, recheck that you applied the correct LimitRange to the correct namespace.
Checkpoint / question

What is the practical difference between “no resources were specified” and “resources were specified above the maximum”?

Module 1

Apply a ResourceQuota and watch a Deployment hit the namespace budget

Now shift from one container at a time to the total budget available inside the namespace.

Objective

Show that a ResourceQuota limits aggregate namespace consumption, even when each individual pod is valid.

Why this matters

A namespace-wide budget helps teams share a cluster fairly. Even if every pod meets the LimitRange, the namespace can still run out of allowed pods, CPU requests, memory requests, or limits.

Review before deploying

In VS Code, open 40-resource-quota.yaml and review the namespace pod, CPU, and memory budgets.

Apply the ResourceQuota and inspect the budget
kubectl apply -f .\manifests\01-limit-ranges-resource-quotas\40-resource-quota.yaml
kubectl describe resourcequota namespace-compute-quota -n $limitNs
Review before deploying

In VS Code, open 50-quota-workload.yaml and compare its requested replica count and resources with the remaining quota.

Create a four-replica Deployment and inspect the result
kubectl apply -f .\manifests\01-limit-ranges-resource-quotas\50-quota-workload.yaml
kubectl get deployment,pods -n $limitNs -o wide
kubectl describe resourcequota namespace-compute-quota -n $limitNs
kubectl get events -n $limitNs --field-selector reason=FailedCreate --sort-by=.lastTimestamp
ResourceQuota

A namespace policy that caps total resource usage across all objects in that namespace.

FailedCreate event

An event emitted when the Deployment controller tries to create a pod but the API server rejects it because the quota would be exceeded.

Command explanation

  • The quota allows only 3 total pods in the namespace.
  • defaulted-pod already consumes one of those three pod slots.
  • The quota-workload Deployment asks for 4 replicas, but only two new pods fit before the namespace reaches its pod and compute budget.
  • kubectl get events shows the controller trying to create more pods and being denied.
Expected output / evidence

The Deployment should remain around 2/4 ready replicas. The ResourceQuota description should show the budget in use, and the FailedCreate events should explain that the namespace exceeded its quota.

Troubleshooting note
  • If more than two workload pods appear, recheck whether defaulted-pod still exists and whether the ResourceQuota was applied successfully.
  • If you do not see events immediately, rerun the final event command. Controllers may need a short moment to retry and report the failure.
Checkpoint / question

Why can a Deployment manifest be valid on its own but still fail to create all requested replicas?

Module 1 knowledge check

Question 1: What problem does the LimitRange solve?

It sets per-container defaults and boundaries, so missing resources can be filled in and oversized containers can be rejected.

Question 2: What problem does the ResourceQuota solve?

It caps total namespace consumption across pods, requests, and limits.

Question 3: Why did the Deployment stop around 2/4 replicas?

Because defaulted-pod already used one of the three allowed pod slots, leaving room for only two more pods before the quota was exhausted.

Module 2

Deploy a workload that intentionally requests more than it needs

VPA is easiest to understand when the starting requests are obviously generous.

Objective

Create the weather API workload with baseline requests of 200m CPU and 256Mi memory on each pod.

Why this matters

Kubernetes scheduling is based on requests, not actual live usage. Over-requesting can waste cluster capacity even when the app is mostly idle.

Review before deploying

In VS Code, review 00-namespace.yaml and 10-workload.yaml. Find the Deployment's starting CPU and memory requests before applying them.

Deploy the VPA demo workload and inspect the configured requests
kubectl apply -f .\manifests\02-vertical-pod-autoscaler\00-namespace.yaml
kubectl apply -f .\manifests\02-vertical-pod-autoscaler\10-workload.yaml
kubectl rollout status deployment/weather-api -n $vpaNs --timeout=120s
kubectl get pods -n $vpaNs -l app=weather-api -o custom-columns="POD:.metadata.name,CPU_REQUEST:.spec.containers[0].resources.requests.cpu,MEMORY_REQUEST:.spec.containers[0].resources.requests.memory"
Request

The amount Kubernetes reserves for scheduling purposes.

Limit

The runtime ceiling. This demo keeps the limits unchanged while VPA focuses on requests.

Command explanation

  • The workload manifest creates two replicas of the weather API.
  • Each pod requests 200m CPU and 256Mi memory, with higher limits.
  • The custom-columns output makes the starting requests easy to compare with the later VPA recommendation.
Expected output / evidence

The Deployment should roll out successfully, and both pods should show requests of 200m CPU and 256Mi memory.

Troubleshooting note
  • If rollout fails, inspect the namespace with kubectl get pods -n $vpaNs and kubectl describe pod -n $vpaNs <pod-name>.
  • If the namespace already had old objects, delete $vpaNs, wait until it is gone, and rerun this step.
Checkpoint / question

Why can an over-requested workload look healthy even when it is using cluster capacity inefficiently?

Module 2

Create the VPA in recommendation-only mode and inspect its advice

Start safely: let VPA recommend without changing the running pods yet.

Objective

Apply a VPA object in Off mode and learn how to read its recommendation fields.

Why this matters

Recommendation-first is the safest way to start with VPA. It gives you data without changing pods or risking surprise restarts.

Review before deploying

In VS Code, open 20-vpa-off.yaml and review the update mode, target Deployment, and resource policy.

Apply the VPA in Off mode
kubectl apply -f .\manifests\02-vertical-pod-autoscaler\20-vpa-off.yaml
kubectl get vpa -n $vpaNs
Read the recommendation when it becomes available
kubectl describe vpa weather-api-vpa -n $vpaNs
kubectl get vpa weather-api-vpa -n $vpaNs -o jsonpath="{.status.recommendation}"

Off mode

The VPA object collects data and computes recommendations, but it does not evict or recreate pods.

What to look for

Lower bound, target, upper bound, and uncapped target. The target is usually the main starting point for discussion.

Command explanation

  • The checked-in VPA policy controls CPU and memory requests only.
  • Its allowed range is intentionally constrained between 25m / 32Mi and 100m / 128Mi.
  • kubectl describe vpa is the most readable view when the recommendation is populated.
  • The JSONPath output is useful when you want the raw recommendation object.
  • Do not combine VPA and HPA on the same CPU or memory signal unless you have designed that interaction very carefully.
Expected output / evidence

At first, the recommendation may be missing or incomplete. After VPA has enough metrics history, the target recommendation should eventually be lower than the original 200m CPU request for this lightweight service.

Troubleshooting note
  • If the recommendation is empty, wait a few minutes and rerun the describe command. That delay is normal.
  • For real production decisions, treat short lab data as a demonstration only. Representative traffic over a much longer window is more trustworthy.
Checkpoint / question

Why is Off mode usually a safer first step than immediately enabling automatic pod recreation?

Module 2

Optionally switch to Recreate mode and verify the new live pod requests

This is the only step in the lab that intentionally changes the running pods based on VPA output.

Objective

Observe how VPA can replace pods so the newly created pods receive recommended requests at admission time.

Why this matters

VPA can help rightsize workloads, but applying those changes can disrupt running pods. That is why teams usually evaluate recommendations first and automate second.

Review before deploying

In VS Code, open 30-vpa-recreate.yaml and identify what changes from the VPA Off-mode manifest before applying it.

Record the current pods, enable Recreate mode, and watch for new pod names
kubectl get pods -n $vpaNs -l app=weather-api
kubectl apply -f .\manifests\02-vertical-pod-autoscaler\30-vpa-recreate.yaml
kubectl get pods -n $vpaNs -l app=weather-api --watch
The watch command keeps running

Wait until you see an old pod terminate and a new pod appear. Then press Ctrl+C to stop the watch and return to the PowerShell prompt before running the next commands.

After new pod names appear, press Ctrl+C and compare live pods with the Deployment template
kubectl get pods -n $vpaNs -l app=weather-api -o custom-columns="POD:.metadata.name,AGE:.metadata.creationTimestamp,CPU_REQUEST:.spec.containers[0].resources.requests.cpu,MEMORY_REQUEST:.spec.containers[0].resources.requests.memory"
kubectl get deployment weather-api -n $vpaNs -o jsonpath="{.spec.template.spec.containers[0].resources.requests}"

Live pods

The new pods should show requests inside the VPA policy bounds rather than the original oversized values.

Deployment template

The Deployment object itself still shows the original requests. The VPA admission controller mutates the new pods as they are created.

Command explanation

  • Recreate allows the VPA updater to evict and replace pods when their current requests differ materially from the recommendation.
  • The demo policy deliberately makes the starting requests above the VPA maximum so replacement becomes visible in a short lab.
  • Watching the pods helps you confirm that names or ages changed.
  • The updater replaces pods gradually, one pod at a time, rather than restarting everything at once.
Expected output / evidence

You should eventually see new pod names or newer pod ages. The live pod requests should fall within the VPA policy range, while the Deployment template still shows the original 200m CPU and 256Mi memory requests.

Troubleshooting note
  • The AKS VPA updater evaluates periodically, roughly around once per minute, so do not expect immediate pod replacement.
  • If nothing changes after a few minutes, rerun kubectl describe vpa weather-api-vpa -n $vpaNs and confirm a recommendation exists.
  • If you do not want any disruption, skip this step and move on. The recommendation-only lesson still stands.
Checkpoint / question

Why is it useful to compare live pod requests with the Deployment template after switching to Recreate mode?

Module 2 knowledge check

Question 1: What is the main difference between Off and Recreate mode?

Off mode recommends only. Recreate mode can evict and replace pods so they come back with VPA-selected requests.

Question 2: Why might the recommendation take time to appear?

Because VPA needs metrics history before it can make a useful recommendation.

Question 3: Why might live pods show different requests than the Deployment template?

Because the VPA admission controller mutates new pods at creation time while the Deployment spec remains unchanged.

A newly started pod may take about a minute to appear in the Metrics API. If kubectl top pods -n $hpaNs reports that metrics are unavailable, wait 30 to 60 seconds and rerun the command. You may need to retry it a few times.

Create the HPA and inspect its initial status
kubectl apply -f .\manifests\03-horizontal-pod-autoscaler\20-hpa.yaml
kubectl describe hpa cpu-demo -n $hpaNs
HPA

The Horizontal Pod Autoscaler changes the number of replicas on a workload.

50% of request

In this demo, the pod request is 50m CPU, so the target is about 25m average CPU per pod.

Command explanation

  • The baseline workload starts with one replica.
  • The pod requests 50m CPU and limits at 250m.
  • The HPA ranges from 1 to 6 replicas and targets 50% average CPU utilization.
  • The checked-in HPA policy allows scale-up by up to 2 pods every 30 seconds and uses a 60-second scale-down stabilization window.
  • Initial HPA CPU status may briefly show <unknown> until fresh metrics arrive.
Expected output / evidence

You should see one cpu-demo pod and an HPA named cpu-demo. The HPA description should show min and max replicas, and it may briefly show <unknown> for current CPU until metrics catch up.

Troubleshooting note

  • If the HPA description shows <unknown> initially, that is normal on a newly created workload.

Module 3

Start the load generator and watch the HPA scale out

Create steady in-cluster demand so the HPA has a clear reason to add replicas.

Objective

Push CPU above the target long enough for the HPA to increase the Deployment replica count.

Why this matters

HPA works best when load is sustained and measurable. This demo uses an in-cluster load generator so the requests naturally flow through the Kubernetes Service to the target pods.

Review before deploying

In VS Code, open 30-load-generator.yaml and review how it sends sustained traffic to the application Service.

Start the load generator and wait for it to become Ready
kubectl apply -f .\manifests\03-horizontal-pod-autoscaler\30-load-generator.yaml
kubectl rollout status deployment/load-generator -n $hpaNs --timeout=120s
Watch the HPA change over time
kubectl get hpa cpu-demo -n $hpaNs --watch
The watch command keeps running

Watch the REPLICAS column increase. When it reaches 3, press Ctrl+C to stop the watch and return to the PowerShell prompt.

After the replica count grows, press Ctrl+C and inspect the pods and their CPU
kubectl get pods -n $hpaNs -l app=cpu-demo -o wide
kubectl top pods -n $hpaNs -l app=cpu-demo

Command explanation

  • The load generator uses the checked-in manifest and sends sustained requests to the cpu-demo Service.
  • It opens fresh HTTP connections so traffic can be balanced across Service endpoints instead of being pinned to one long-lived connection.
  • kubectl get hpa --watch is the clearest live view of scaling decisions during this demo.
  • When new pods are added, traffic is shared and the average CPU utilization should move back toward the target.
Expected output / evidence

Within roughly 30 to 90 seconds, the HPA should usually raise the replica count above one. After you exit the watch, kubectl get pods should show multiple cpu-demo pods.

Troubleshooting note
  • If the HPA does not scale right away, give it more time. Metrics collection and HPA decisions are periodic, not instant.
  • If the load generator rollout fails, describe its pod to inspect image pull or scheduling problems.
  • If pod CPU values still do not appear, fix the metrics pipeline first; HPA depends on it.
Checkpoint / question

Why is sustained demand more useful than a quick one-second spike when demonstrating HPA?

Wrap-up

Stop the load, watch scale-down, then clean up all demo namespaces

Finish by proving that HPA can scale back in and by leaving the cluster clean for the next student.

Objective

Remove the demand source, observe HPA scale-down behavior, and clean up every namespace used in the lab.

Why this matters

Good demos end cleanly. Scale-down is intentionally slower than scale-up, and student cleanup should remove only the demo namespaces, not cluster-level features like the VPA add-on.

Stop the load and watch the HPA scale down
kubectl delete deployment load-generator -n $hpaNs
kubectl get hpa cpu-demo -n $hpaNs --watch
The watch command keeps running

Scale-down is slower than scale-up. Watch the REPLICAS column and, when the replica count drops, press Ctrl+C to stop the watch and return to the PowerShell prompt.

After the replica count falls back, press Ctrl+C and inspect the HPA one last time
kubectl describe hpa cpu-demo -n $hpaNs
kubectl get deployment cpu-demo -n $hpaNs
kubectl get pods -n $hpaNs -l app=cpu-demo -o wide
Final student cleanup
kubectl delete namespace $limitNs --ignore-not-found=true
kubectl delete namespace $vpaNs --ignore-not-found=true
kubectl delete namespace $hpaNs --ignore-not-found=true

Command explanation

  • Deleting the load generator removes the sustained CPU demand.
  • HPA scale-down is conservative and uses a stabilization window, so it may take a few minutes to return to one replica.
  • The final cleanup removes the three demo namespaces only. It does not disable the cluster-level VPA add-on.
Expected output / evidence

HPA should eventually move back toward its minimum replica count. The cleanup commands should start namespace deletion for aks-governance-demo, aks-vpa-demo, and aks-hpa-demo.

Troubleshooting note
  • Scale-down may take several minutes because the HPA waits for metrics to fall and for the stabilization window to expire.
  • If a namespace stays in Terminating, inspect remaining objects or finalizers before retrying the lab.
  • If you enabled VPA earlier, leave it enabled unless the cluster owner tells you otherwise.
Checkpoint / question

Why is the correct student cleanup “delete the namespaces” rather than “undo every cluster-level feature change”?

Module 3 knowledge check

Question 1: What signal tells the HPA to add replicas in this demo?

Average CPU utilization across ready pods, measured as a percentage of each pod's CPU request.

Question 2: Why can scale-down feel slower than scale-up?

Because HPA uses fresh metrics plus a stabilization window to avoid flapping.

Question 3: What is the difference between VPA and HPA in one sentence?

VPA changes or recommends per-pod CPU and memory requests; HPA changes the number of pod replicas.
